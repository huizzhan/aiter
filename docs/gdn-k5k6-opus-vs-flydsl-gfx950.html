GDN prefill 融合 K5+K6：opus WF vs FlyDSL VK (PR #4884)

AMD Radeon Graphics · gfx950:sramecc+:xnack- · 256 CU · bf16 · K=V=128 · BT=64 · GQA 4（Hk=16 / Hv=64）· packed varlen · 两侧都是 output_final_state=True + 真实 initial_state · 每格 50 次取中位、profiler 20 次取 device time

融合 kernel 上游限定 gfx942。PR #4884 的融合 K5+K6 （gdn_fused_gfx942_kernels.py）对非 gfx942 直接拒绝，自带的单元测试也整套 skip。本页是放开 arch 门控之后在 gfx950 上测的，测之前先把 PR 那 114 个融合用例在本卡跑过一遍（113 passed / 1 skipped，含 bv16/32/64/bv64w8 各变体、非 BT 倍数尾块、tail-mask 的 Inf/NaN 隔离、final_state 一致性）。

前端是 Triton 而非 FlyDSL。FlyDSL 的 gdn_prepare 需要 flydsl.expr.gpu.shuffle，本机装的 flydsl 0.2.4 没有这个符号。融合 K5+K6 本身不用 shuffle，所以 K5+K6 那一列不受影响；wall 一列两边前端不同，只能参考。

auto 的变体选择在这张卡上不是最优。60/64 格里 auto 选的 BV 与变体探针（probe_fused_variant.py）在本卡实测最优的那个不同，平均慢 1.27x。右侧「按 CU 缩放的变体」列是换成实测规则之后的结果。

按 B·H 汇总

整块 pipeline 的 wall

K5+K6 之外两条 pipeline 的前端也不同：opus 把 K1..K4 融进一个 HIP kernel（gdn_k1_neumann_kernel），FlyDSL 这边是 Triton prepare 三件套， 两者之比 geomean = 0.50x。

as-shipped 全 pipeline：geomean(opus/FlyDSL) = 0.879， FlyDSL 赢 19/64 格。 K5+K6 单看是 geomean 1.170（修正变体后 1.461）。
